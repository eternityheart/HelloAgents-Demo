# 💼 常见面试问题与回答

## 一、项目概述类

### Q1: 请简单介绍一下这个项目
> **回答模板**:
> 
> "这是一个基于 **HelloAgents 框架** 的多智能体旅行规划系统。
> 
> 核心功能是让用户用自然语言描述旅行需求（如'北京3日游，喜欢历史'），系统自动调度多个专家 Agent 协作，生成包含景点、餐厅、酒店的结构化多日行程。
> 
> 技术上采用 **Orchestrator-Workers** 模式，后端用 FastAPI 实现 SSE 流式输出，前端用原生 JS 实现对话和地图可视化。"

---

### Q2: 为什么选择这个项目？
> "我选择这个项目有三个原因：
> 1. **技术深度**: 涵盖 LLM 应用开发的完整链路（Prompt Engineering → Agent编排 → 工具调用 → 前后端集成）
> 2. **工程实践**: 不是简单的 API 调用，而是真正落地了 Agentic Workflow
> 3. **面试增值**: 能体现我对 AI-Native 应用架构的理解"

## 二、技术架构类

### Q3: 解释一下 Orchestrator-Workers 模式
> "这是一种常见的 Multi-Agent 架构：
> 
> - **Orchestrator (编排器)**: 相当于'大脑'，负责理解用户意图、分解任务、调度工具、整合结果
> - **Workers (执行器)**: 相当于'手脚'，每个 Worker 专注于一个垂直能力（如搜索、天气、酒店）
> 
> 优势在于职责解耦：Orchestrator 不需要知道如何调用高德 API，只需要知道'有一个工具能搜景点'就行了。"

---

### Q4: MCP 协议是什么？有什么好处？
> "**Model Context Protocol** 是一种工具标准化协议，核心思想是让 Agent 和工具之间通过统一的 JSON Schema 通信。
> 
> **优势**:
> 1. **降低集成成本**: 传统方式每个 API 需要单独适配，MCP 让工具可复用
> 2. **动态发现**: Agent 可以在运行时发现有哪些工具可用
> 3. **跨模型复用**: 同一套工具可以被不同 LLM 使用
> 
> 在我的项目中，我用 FastMCP 库实现了工具封装，通过 `@mcp.tool()` 装饰器注册。"

---

### Q5: 为什么用 FastAPI 而不是 Flask？
> "主要原因是 **异步性能** 和 **SSE 支持**：
> 
> 1. Agent 推理通常需要 10-30 秒，Flask 是同步框架会阻塞其他请求
> 2. FastAPI 原生支持 async/await，可以处理长时任务
> 3. SSE（Server-Sent Events）用于流式输出，让用户实时看到 Agent 思考过程
> 4. 自动生成 Swagger 文档，方便调试"

---

## 三、技术难点类

### Q6: 如何处理 LLM 幻觉（Hallucination）问题？
> "我采用了三层防御策略：
> 
> **1. Prompt 层**:
> 明确指令：'只使用工具返回的真实数据，不要虚构'
> 
> **2. 数据校验层**:
> 使用 Pydantic 对 LLM 输出进行强类型校验，不符合 Schema 的直接拒绝
> 
> **3. 业务逻辑层**:
> 对关键字段（如坐标）进行范围检查，确保在目标城市范围内
> 
> 效果是大幅降低了虚构景点的情况。"

---

### Q7: SSE 和 WebSocket 有什么区别？为什么选 SSE？
> "| 特性 | SSE | WebSocket |
> |-----|-----|-----------|
> | 方向 | 单向（服务器→客户端）| 双向 |
> | 协议 | HTTP | 独立协议 |
> | 重连 | 自动 | 需手动实现 |
> | 复杂度 | 低 | 高 |
> 
> 我的场景是'用户提问 → Agent 流式回复'，只需要单向推送，SSE 足够且更简单。
> 如果需要实时双向通信（如聊天室），才需要 WebSocket。"

---

### Q8: 多 Agent 之间如何协调？会不会冲突？
> "目前采用的是 **串行+并行混合** 模式：
> 
> 1. **意图理解**: Orchestrator 先解析用户需求
> 2. **并行调用**: 同时触发 Weather/Scout/Hotel 三个 Agent
> 3. **结果整合**: 等所有 Agent 返回后，由 Orchestrator 统一融合
> 
> 不会冲突因为：
> - 每个 Agent 只负责自己的领域
> - 没有共享状态需要竞争
> - Orchestrator 是唯一的协调者"

## 四、扩展问题类

### Q9: 如何扩展新的 Agent？
> "扩展非常简单，只需三步：
> 
> **Step 1**: 创建新文件 `xxx_agent.py`
> ```python
> @mcp.tool(description='xxx')
> def new_tool(...):
>     return result
> ```
> 
> **Step 2**: 在 Orchestrator 的 System Prompt 中添加工具说明
> 
> **Step 3**: 在 `_handle_tool_call` 中添加调用逻辑
> 
> 整个过程不需要修改现有 Agent 代码，符合开闭原则。"

---

### Q10: 如果要部署到生产环境，还需要做什么？
> "主要有四个方向：
> 
> 1. **容器化**: 编写 Dockerfile，用 docker-compose 管理多服务
> 2. **API 熔断**: 对高德 API 添加限流和熔断机制，防止 429 错误
> 3. **缓存层**: 对天气等不常变化的数据加 Redis 缓存
> 4. **监控告警**: 添加日志收集和 APM 监控
> 
> 这些在我的 Phase 10 扩展计划中都有规划。"
