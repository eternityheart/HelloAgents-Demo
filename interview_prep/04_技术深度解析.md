# 🔬 技术深度解析

## 一、核心技术栈详解

### 1.1 LLM 调用链路

```
用户输入
    ↓
┌─────────────────────────────────────┐
│  System Prompt (角色定义 + 工具说明)  │
│  + User Message (用户输入)           │
│  + History (对话历史)                │
└──────────────┬──────────────────────┘
               ↓
         DeepSeek API
               ↓
     response_format={"type": "json_object"}
               ↓
┌─────────────────────────────────────┐
│  { "type": "tool_call",             │
│    "tool_name": "search_poi",       │
│    "args": {"city": "北京"} }       │
└──────────────┬──────────────────────┘
               ↓
         执行真实工具
               ↓
       工具结果注入记忆
               ↓
       再次调用 LLM 生成回复
```

**关键设计决策**:
- 使用 `response_format={"type": "json_object"}` 强制 JSON 输出
- 设置 `temperature=0.1` 降低随机性，提高确定性
- 工具结果通过 `role: user` 注入，兼容性更好

---

### 1.2 Function Calling vs ReAct

| 特性 | Function Calling | ReAct (本项目采用) |
|-----|-----------------|-------------------|
| 工具定义 | 作为 API 参数传入 | 写在 System Prompt |
| 调用方式 | LLM 返回特殊格式 | LLM 返回 JSON 自行解析 |
| 灵活性 | 依赖 API 支持 | 完全自定义 |
| 透明度 | 黑箱 | 完全可控 |

**为什么选 ReAct**:
DeepSeek 的 Function Calling 支持有限，自定义 JSON Schema 更灵活可控。

**问题**: LLM 推理耗时 10-30 秒，用户感知为"卡死"

**解决方案**: Server-Sent Events 实时推送

```python
# 后端
async def chat_generator(message: str):
    yield f"data: 🤔 正在思考...\n\n"
    
    result = await llm_call(message)
    
    yield f"data: {result}\n\n"
    yield "data: [DONE]\n\n"

# 前端
const reader = response.body.getReader();
while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    // 解析并展示

```

### 2.2 多 Agent 并行调用

**问题**: 串行调用 Weather → Scout → Hotel 耗时过长

**解决方案**: asyncio 并发

```python
async def generate(self, city, days, preferences):
    # 并行调用
    weather_task = asyncio.create_task(self._get_weather(city))
    attractions_task = asyncio.create_task(self._search_attractions(city))
    hotels_task = asyncio.create_task(self._search_hotels(city))
    
    # 等待所有完成
    weather = await weather_task
    attractions = await attractions_task
    hotels = await hotels_task
    
    # 整合结果
    return self._combine(weather, attractions, hotels)
```

**效果**: 3 个 API 调用从 15s 降到 5s（取最长者）

### 2.3 Pydantic 数据校验

**问题**: LLM 输出格式不稳定，可能缺字段或类型错误

**解决方案**: Pydantic 强类型模型

```python
class DayPlan(BaseModel):
    day: int = Field(description="第几天")
    weather: str = Field(default="未知")
    morning: List[POI] = Field(default_factory=list)
    
    # 自动校验
    @validator('day')
    def day_must_be_positive(cls, v):
        if v < 1:
            raise ValueError('day must be >= 1')
        return v
```

**优势**:
- 自动类型转换
- 缺失字段使用默认值
- 校验失败抛出明确错误

## 三、性能优化点

### 3.1 Token 消耗优化

| 优化措施 | 节省量 |
|---------|-------|
| 精简 System Prompt | ~30% |
| 只返回必要字段 | ~40% |
| 工具结果压缩 | ~20% |

**示例**: 景点搜索只返回 `name, rating, address`，不返回完整 POI 数据

---

### 3.2 缓存策略

```python
class ItineraryGenerator:
    def __init__(self):
        self.weather_cache = {}  # 天气缓存 (TTL: 1小时)
    
    async def _get_weather(self, city):
        if city in self.weather_cache:
            return self.weather_cache[city]
        
        result = await api_call(city)
        self.weather_cache[city] = result
        return result
```

**适合缓存**: 天气 (变化慢)、POI 基础信息
**不适合缓存**: 酒店价格 (实时变化)
